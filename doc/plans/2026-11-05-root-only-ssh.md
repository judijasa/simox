# Root-only SSH: drop `<app_user>` authorized_keys — Plan & Progress

Date: 2026-11-05
Repos: simox (this repo, consumer); php_daas_framework (../php_daas_framework,
       upstream mechanism); the private config repo (private docs — tracked
       separately).

## Decision

Drop SSH access for the unprivileged app user (`PROD_USER`) entirely. The
operator machine SSHs to prod **as root only**, with the single project key
(`~/.ssh/simox-sshkey`); commands that must run as the app user are run as
`root` and then `sudo -u <PROD_USER>` (or `su`). The app account remains —
created with `useradd --create-home`, password locked — but holds no
`authorized_keys` and has no login path.

Rationale: the repo is operated by a single admin (or a team that already
holds root on every host), so the key authenticates the *operator machine*,
not a remote role. An `authorized_keys` on `<app_user>` is a second credential
surface with no isolation benefit once everyone has root. Today only two steps
in the whole deploy connect as `<PROD_USER>`; both move to `root`, with the
app-user-only work narrowed to `sudo -u`.

## Current app-user SSH surface

`deploy` and every other operator CLI (`tmux-remote`, `gen-firewall`,
`gen-service-accounts`, `replica-bootstrap`, `pf-host`) already connect as
`root`. Only two call sites in `php_daas_framework/bin/deploy` use `PROD_USER`
as an SSH user:

- `deploy_nix_packages` → `nix copy --to "ssh://$PROD_USER@$REMOTE_HOST"`
- `deploy_composer_dependencies` → `ssh ... "$PROD_USER@$REMOTE_HOST" ... composer install`

and `install_nix_remotely` records `trusted-users = root $PROD_USER` (needed
only because the closure copy ran as `PROD_USER`).

## Changes

### php_daas_framework (../php_daas_framework)

- [ ] `bin/deploy` — `deploy_nix_packages`: `nix copy --to
      "ssh://root@$REMOTE_HOST" ./result`. With the multi-user daemon the
      store is written by `nix-daemon` (root); `PROD_USER` never runs nix, so
      it needs no `trusted-users` entry.
- [ ] `bin/deploy` — `install_nix_remotely`: `trusted-users = root` (drop
      `$PROD_USER`).
- [ ] `bin/deploy` — `deploy_composer_dependencies`: ssh as `root`, then run
      `sudo -u "$PROD_USER" -- composer install` so `vendor/` stays owned by
      the app user. Composer must resolve via the nix result bin, so preserve
      `PATH` across the sudo (`sudo --preserve-env=PATH` or `su -s /bin/bash
      "$PROD_USER" -c`).
- [ ] `bin/pf-provision.sh` — assert message/comment: the app user must exist
      but no longer needs SSH access.
- [ ] `etc/deploy.conf.template` — `PROD_USER` comment: "must already exist
      … with SSH access" → drop the SSH-access clause.
- [ ] `doc/system/deploy.md` — drop the "Install SSH access for that user"

## Open items

- **key generation** — `~/.ssh/simox-sshkey` is generated by hand today
  (`ssh-keygen -t ed25519 -N '' -C simox -f ~/.ssh/simox-sshkey`, documented
  in the private config repo's own ssh-keys doc §1); `gen-ssh-config` only *writes*
  the `IdentityFile` line and never generates the key. Whether/where to
  automate generation (e.g. in `make dev-init`) is a separate discussion, and
  is the model the hlab `create-prod-user` client would mirror.
- **`trusted-users`** — dropping `PROD_USER` is safe only while nothing runs
  nix as `PROD_USER`; confirm no cron/app path does before landing.
- **composer as root vs `sudo -u`** — deps are all public HTTPS (no git-auth),
  so `sudo -u` is purely for `vendor/` ownership; `root` + `chown -R
  "$PROD_USER:$PROD_USER" vendor/` is the fallback if `sudo` is undesirable.
