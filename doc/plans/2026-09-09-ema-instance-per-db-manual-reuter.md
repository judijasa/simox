# Adapt to ema instance-per-db + manual reuter.ini — Plan & Progress

Date: 2026-09-09
Repos: simox (this repo); ../php_daas_framework (upstream framework);
       ../ema (upstream). Private config-repo data is tracked in the private
       config repo's own plan doc.

## Decision

simox adapts to the framework's move of MariaDB instance provisioning from
deploy-time to database-creation time (one instance per database). The
framework stops provisioning MariaDB and stops generating connectivity:
`ema create` now provisions the instance and returns its connectivity values,
and `reuter.ini` becomes a manually-maintained private file injected by
`fetch-private-data` (like `machines.ini`), not regenerated by `gen-reuter`
on every deploy.

Concretely for simox: `etc/deploy.conf` drops `DEPLOY_DB_BASE`/
`DEPLOY_DB_INSTANCE`/`DEPLOY_DB_PORT`/`DEPLOY_DB_BIND` (the framework no
longer provisions `/var/lib/simox/mariadb` or the `mariadb@simox` unit);
`etc/reuter.ini` stays git-ignored but is now injected private data;
`bin/gen-service-users` stops writing the `<ACCOUNT>_PASSWORD` keys back into
reuter.ini (that file is now the manual source of truth) and only applies the
account/grants SQL. The `db:<name>` tag remains in `etc/machines.ini` purely
as the advisory anchor for the framework's new warn-only `db-check`.

See
`../php_daas_framework/doc/plans/2026-09-09-ema-prod-instance-at-create-manual-reuter.md`
for the framework-side mechanism (Phases 1–3: ema instance-at-create, removal
of deploy-time provisioning + `gen-reuter`, and the warn-only `db-check`).

This supersedes the one-instance-per-project, provision-at-deploy model in
`doc/plans/2026-08-20-mariadb-instance-per-project.md`, and adjusts the
service-user mechanism from
`doc/plans/2026-09-07-ema-schema-only-and-service-users.md` (account creation
stays; key-writing into reuter.ini goes away).
