# Env Relocation — flake shellHook → Makefile-generated `.env` (Plan & Progress)

## Decision

Make **php_daas_framework** the single source of truth for the **generic
dev-init machinery** — `.env` generation, MariaDB cluster init, and the
dev-shell runtime bootstrap — so that:

1. **php_daas_framework standalone** (used from a fork) works exactly like a
   consumer repo: no env exports in `flake.nix` shellHook; env vars live in a
   git-ignored `.env` generated by `make dev-init`.
2. **Consumers (simox)** delegate to the framework's shipped scripts instead
   of re-implementing the same Makefile + `bin/dev/` scripts.

The framework owns the **mechanism**; the consumer owns all **data and
policy**. The scripts derive everything from the target directory at runtime
(`REPO_PATH` = canonicalized target dir; `REPO_LOG`/`MYSQL_*` under `var/`;
`REUTER_INI = $REPO_PATH/etc/reuter.ini`) — no consumer paths are baked in.
Consumer static config stays in consumer-owned files the framework already
reads (`etc/env.prod` for `gen-env`, `etc/deploy.conf` for `deploy`,
`etc/reuter.ini` for `Database`), and consumer-specific **steps** (git hooks,
hosts, ...) stay in the consumer's Makefile — `init-git-hooks.sh` is a good
example of a consumer-side script.

A consumer-side customization/override mechanism for dev-init ("downstream
overrides settings", config-file style) is a **desired future feature** — the
design stays extensible (parameterized scripts, scripts on PATH) but it is
**not built in this change**.

## How the machinery works before / after

**Before:**

- `php_daas_framework/flake.nix` shellHook `export`s `REPO_PATH`, `REPO_LOG`,
  `REUTER_INI`, `EMA_TARGET`, `MYSQL_*` and runs `mariadb-install-db` +
  starts the daemon inline. No `Makefile`, no `bin/dev/`, no dev `.env`
  generation (README told you to `printf` one manually).
- simox re-implements the whole dev-init chain in its own repo
  (`Makefile`, `bin/dev/init-local-env.sh`, `bin/dev/init-cluster.sh`).

**After:**

- Framework ships `init-local-env.sh`, `init-cluster.sh`, `shell-enter.sh` in
  `packages.default` (`$out/bin/`, on PATH for consumers). Dev shells source
  `shell-enter.sh` (loads `.env`, resumes MariaDB). `make dev-init` writes
  `.env` (dev) — the same split `gen-env` already provides for prod.
- simox's Makefile delegates the generic steps to the framework scripts and
  keeps only its consumer-specific steps (git hooks, hosts).

## Notes

- **Push-before-deploy:** simox's flake pins
  `github:judijasa/php_daas_framework` — the new scripts must be pushed before
  simox's `nix develop` picks them up (`--override-input` for local testing).
- **`.env` drift:** the framework's `init-local-env.sh` must produce
  byte-identical output to simox's current script (checked in Phase 2).
- **simox `_dev-assert-nix`:** its multi-line `if` recipe lacked backslash
  continuations (each Make recipe line runs in its own shell), so
  `make dev-init` always failed at that target; fixed to match the
  framework's reference implementation during Phase 2 verification.
- **`ema` quirk:** `ema init db <name>` drops into an interactive `mariadb`
  client after bootstrapping — in non-interactive runs it blocks on stdin
  (worked around with `</dev/null`). Pre-existing ema behavior.
- **`nix develop --command` runs the shellHook but not the stop trap**
  (verified in Phase 2): MariaDB resumes for scripts/CI, yet the EXIT trap
  does not fire in `--command` mode — the daemon keeps running after the
  shell exits (stop it manually; interactive `nix develop` shells still stop
  the daemon on exit via the trap).
- **`ema` needs the vars right after `make dev-init`** (the shellHook only runs
  on shell entry) — README documents `source .env` / re-enter the shell; same
  constraint already exists in simox.
- **Future (not built):** consumer customization/override mechanism for
  dev-init; framework `Makefile` shipped for `-include` by consumers;
  framework-owned `init-git-hooks.sh` (pre-commit install).
