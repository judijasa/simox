# TLS client certs for remote DB connections — cross-repo plan (handoff)

Working note: the cross-repo plan source. To be translated into one dated plan
per repo (`php_daas_framework`, `ema`, `simox`) — see "Next step". Intended to
be dropped at the repo root as an untracked scratch file.

Date: 2026-09-28 (refined 2026-09-29)

## Why we are here

An old `gen-service-accounts` was applied against `simo0`, creating three
passwordless, host-pinned accounts (`'simox'@'10.99.233.10'`, `.181`, `.81`).
The framework pin is now current (`php-daas-framework#bacff56`, `ema#2b64bf43`),
which supports an optional `require` clause in `RolesConfig` — emitted as
`REQUIRE <value>` on every `CREATE USER`/`ALTER USER`. The goal is to re-run the
reconcile with certificates required.

## Directive (agreed)

> Any remote connection should support certification in case it is required.

Opt-in per connection; nothing declared = plain TCP exactly as today. The
driving purpose is **machine identification without spoofing risk** (see
"Agreed so far"), on top of the single-`simox`-account model.

## The picture

| Who | Runs where | How it reaches the DB | Affected by `REQUIRE X509`? |
|---|---|---|---|
| PHP app (indexer/pipeline cron) | `simo0` `.181` | TCP → `simo0:33705` as `simox` | yes |
| PHP app (website) | `simo1` `.242` | TCP → `simo1` as `simox` | yes (on simo1) |
| Operator, ad hoc | `.81` / `.10` | TCP as `simox` | yes |
| `gen-service-accounts`, `ema mariadb` | dev machine → host | ssh + root over the instance socket | no |
| Replication thread | `simo1` → `simo0` | `CHANGE MASTER` as `replication` | only if that account is certed |

Two halves, and they are independent:

- **Server half** — `simo0` must (i) present TLS (already: `have_ssl=YES`, certs
  auto-generated by MariaDB 11.8) and (ii) trust a CA so it can *verify* client
  certs (`ssl-ca` in `/etc/simo0/my.cnf`, written by ema's `_prod_write_conf()`).
  Without `ssl-ca`, `REQUIRE X509` authenticates nobody → all three accounts die
  at once.
- **Client half** — each connecting program needs a cert+key and must hand them
  to its driver. The minimum for the stated goal is **cert+key only** (the client
  *presents*, the server verifies): PHP/mysqlnd via `MYSQL_ATTR_SSL_CERT/KEY`
  (framework `Utils\Connectivity\Database`); the `mariadb` CLI via
  `~/.my.cnf.d/simox.cnf` (`[client] ssl-cert/ssl-key`, read automatically — no
  code); the replication thread via `MASTER_SSL_CERT/KEY` (ema). Client-side
  **`ssl-ca` is a separate concern** (the client verifying the *server*) — see
  "Open items".

## Verified facts

- Dry run `vendor/bin/gen-service-accounts simo0 -n` emits the same passwordless
  SQL as the old run (no `REQUIRE`), because
  `pkg/roles-D0YRR7WII6V1XDZR/default.php` passes no `require`. Account set
  matches what is live; only extra statement is
  `DROP USER IF EXISTS 'simox'@'10.99.233.242'` (web host, never created there).
- **No ad-hoc SQL is needed**: the reconcile's `ALTER USER … IDENTIFIED BY ''
  REQUIRE X509` rewrites the three existing rows in place.
- `simo0`: `ssl_ca`/`ssl_cert`/`ssl_key` empty, `have_ssl=YES`,
  `/etc/simo0/my.cnf` has no `ssl*` keys, `require_secure_transport=OFF`.
- `juan-workstation` (`.81`) has no `~/.mariadb/` and no `~/.my.cnf` — no client
  cert material exists anywhere yet.
- ema owns the instance config: `_prod_write_conf()` writes
  `${EMA_PROD_CONF_DIR:-/etc}/<db>/my.cnf` (an `<extra>` arg is already appended
  verbatim, used by the replica build). `DatabaseConfig` carries
  `replica_ssl_verify_server_cert`, but that key is per-database and
  replica-only (the constructor rejects it unless `type=replica`) — it does not
  transfer to a host-level value.
- ema has no host-level config file: its host-level knobs are env vars
  (`EMA_PROD_BASE`/`CONF_DIR`/`USER`/`BIND`, all framework-defaulted), and its
  only consumer-owned file is `reuter.ini` — per-database connection values
  (`SERVER`/`PORT`/`MYSQL_UNIX_PORT`).
- framework owns the app-side connection: `Database::connectAs()` builds a plain
  DSN, `baseOptions()` carries no SSL attributes; mysqlnd does not read
  `~/.my.cnf`, so paths must be passed explicitly.
- Precedent for "a path in an env file": `REUTER_INI` in prod `.env`
  (regenerated by the framework's `gen-env` from `deploy.conf`) and injected into
  php-fpm as `env[REUTER_INI]`, because php-fpm has no `.env`.
- **`gen-cert` already exists** (framework `bin/gen-cert`), now orphaned: the
  member flow moved to passwords
  (`php_daas_framework/doc/plans/2026-09-28-password-team-and-cert-service-accounts.md`),
  and its subject source (`etc/team.ini` `subject` key) is gone. Its shape is the
  one to reuse: key+CSR generated on the machine, CA key offline, operator signs,
  then `install` puts cert+key under `~/.mariadb/` and points `~/.my.cnf`
  `[client]` at them.
- **None of the target client config exists yet** — there is no `etc/dev.conf`,
  no `DEV_MYSQL_SSL_DIR`, no `~/.simox/ssl/`, no `~/.my.cnf.d/` drop-in. Today
  `make dev-init` runs `init-local-env.sh` (writes `REPO_PATH`/`REPO_LOG` to
  `.env`) and appends `export DBUSER=simox`. The `dev.conf` design is the
  *target*, not current state.
- **The registries are keyed by ZeroTier IP**, and the names are simox-local
  labels (`simo0`/`simo1` in `etc/hosts`; `juan-workstation`/`juan-laptop` in
  `etc/team.ini`) — **not** the ZeroTier node name.

## Agreed so far

- The `require` clause is consumer-side data; making certs *usable* is framework
  (client) + ema (server) work.
- **Purpose: identify which machine is accessing a DB, spoof-resistantly.** A
  host-pinned source IP can be spoofed; a private key cannot. The network relies
  on a single `simox` account across databases (exceptions: root via socket, and
  the `replication` account), so "who" = "which host".
- **One client cert per machine**, reused across every account and database on
  that host — not one per link. The subject's CN is the **pinned simox-local
  name** (the hostname in `etc/hosts` for prod hosts, the machine name in
  `etc/team.ini` for operator machines — never the ZeroTier node name). That is
  what makes the machine identifiable in the handshake and audit log.
- **No GUID in the CN.** The member flow's `<username>-<guid>` CN was load-bearing
  because `REQUIRE SUBJECT` pinned the exact DN, so rotation required a new
  subject. `REQUIRE X509` never matches the subject, so a GUID adds noise to the
  one human-readable field and no enforcement value; per-issuance uniqueness
  already lives in the cert's serial number. Revisit only if a future plan moves
  to `REQUIRE SUBJECT` (per-machine access control).
- **`REQUIRE X509` is a membership gate, not identity.** It checks only "signed
  by the trusted CA". Identity is delivered by the existing host pin
  (`'simox'@'10.99.233.X'`) *plus* the cert subject recorded in the audit log —
  not enforced. A single multi-host `simox` account rules out `REQUIRE SUBJECT`
  (one exact subject per account), so cert identity is audit-level, not
  per-machine access control.
- **Per-project isolation = per-project CA, not the subject.** `REQUIRE X509`
  accepts any cert signed by the server's CA, so two projects sharing a CA would
  accept each other's certs regardless of subject. Simox runs its own CA; every
  cert is signed by it, and each project's DB servers set `ssl-ca` to their own
  CA. "One cert per machine *per project*" falls out of this — the CA scopes the
  cert to the project, the CN scopes it to the machine.
- **The cert path is a conventional directory, not per-machine config.** The
  path is a category-level constant; the per-machine artifact is the cert
  *content* (subject). Two categories, two drivers, two paths:
  - service (framework PHP app, replication) → `/etc/simox/ssl/`, stated as a
    consumer option in `deploy.conf` and delivered to the app via `gen-env` →
    `.env` → php-fpm `env[...]` (the `REUTER_INI` precedent);
  - human (operator/dev `mariadb` CLI) → `~/.simox/ssl/`, stated in a
    `~/.my.cnf.d/simox.cnf` drop-in written idempotently, mirroring the existing
    `~/.ssh/config.d/<repo-dir>.conf` generation (`gen-ssh-config`).
  `reuter.ini` is out of the cert-path picture entirely: it is DB-instance
  connection data, keyed by database, not by machine.
- **The client cert helper is a repurposed `gen-cert`.** It becomes the
  machine-cert CLI (CN = pinned name, no GUID); the member/`subject`-from-
  `team.ini` path is retired. Key material stays on the machine; the CA key is
  offline; the only travel is the CSR out and the signed cert back.
- **Dev-side consumer options live in `etc/dev.conf`**, and **the `dev.conf`
  mechanism moves to the framework** (committed `etc/dev.conf.template` is the
  how-to-write reference; the real file is materialized by `fetch-private-data`
  or hand-copied — the `deploy.conf` pattern). It holds only non-derived,
  consumer-chosen dev values (today `DBUSER`, `DEV_MYSQL_SSL_DIR`; grows as
  needed). Derived values (`REPO_PATH`, `REPO_LOG`, sentinel tags) stay derived —
  `dev-init` keeps favouring derivation. The *values* stay consumer data.
- Getting the key onto a host is a **provisioning** action (once per host, again
  on rotation), not a per-connection one. Per connection, only the **path** is
  needed. Scope: server cert/key + CA cert (`ssl-ca`) on DB hosts only; client
  cert/key on every host that connects. Key material is never shipped via config
  — only paths.
- **Cert material is prod-only; the dev sandbox stays plain TCP.** Dev machines
  are clients (present cert+key only — they never hold the CA cert) and also
  hosts of a local *sandbox* (`ema sandbox`, `ema create --from-snapshot`), but
  that sandbox is schema-only (ema dropped user/grants emission) — no `REQUIRE`,
  no `ssl-ca`. The only client-verifies-server code is
  `replica_ssl_verify_server_cert` (replication), off by default. So
  `REQUIRE X509` + `ssl-ca` apply to prod DB hosts only.
- **ema server side = paths only.** ema reads `ssl-ca = <path>` from a
  consumer-owned **host-level config file** — `etc/ema.conf.template` (committed,
  a `[default]` section carrying `ssl-ca = <path>`) materialized to
  `etc/ema.conf` (gitignored; shipped by `fetch-private-data` or hand-copied, the
  `reuter.ini.template`/private `reuter.ini` delivery pattern). Host-level — one
  value shared by every DB on the host — so it does not belong in the
  per-database `DatabaseConfig` or the per-database `reuter.ini` sections. ema
  emits it into `<db>/my.cnf`'s `[mysqld]` block via the existing
  `_prod_write_conf` `<extra>` append: `ssl-ca` set → emit; unset/absent → plain
  TCP. The **public CA cert** file is installed out-of-band by the operator
  (`scp`) to the path named in `etc/ema.conf`; ema never copies certificate
  bytes. `require_secure_transport` stays deferred.
- **Private-key delivery is out-of-band.** A private key never ships with the
  repo or via `DEPLOY_PRIVATE_FILES`; only the public cert travels back to the
  machine.
- The `SIMOX_PASSWORD` gap in the private `etc/reuter.ini` is parked for now.
  (Finding: `Database::connectAs()` requires the `<ACCOUNT>_PASSWORD` key to
  exist — empty = passwordless; the private sections carry only
  `SERVER`/`PORT`/`MYSQL_UNIX_PORT`.)

## Open items

- **Revocation is absent.** `REQUIRE X509` + an offline CA + no CRL means a
  leaked machine cert currently cannot be revoked at all. This is the real gap
  behind "rotate on leak", and the CN naming is orthogonal to it. Settle before
  implementation (a CA-side/CRL mechanism, not a naming change).
- **Client-side server verification — out for v1, recorded as a real follow-up
  (not dismissed).** The client's `ssl-ca` (`MYSQL_ATTR_SSL_CA`, `[client]
  ssl-ca`) is the client verifying the *server*. The two directions are symmetric
  in difficulty (both need an in-network IP hijack) but not in cost or impact: we
  already mint CA-signed *client* certs, so server-verifies-client is nearly free
  once the CA exists; the reverse needs CA-signed *server* certs on every DB host
  (replacing MariaDB's auto-gen self-signed ones) plus `ssl-ca` on every client —
  the genuinely extra work. Impact also differs: a spoofed client reads/writes
  the DB directly; a spoofed server MITMs one client's session. v1 ships
  server-verifies-client only (client presents cert+key; server verifies). Full
  mutual TLS is the follow-up, deferred on cost, not dismissed on difficulty.
- **Replication channel** — only if the `replication` account is certed;
  otherwise defer (still open in the earlier ema plan). `replica-bootstrap`
  creates it passwordless and host-pinned; the `CHANGE MASTER` already emits
  `MASTER_SSL_VERIFY_SERVER_CERT` but no client cert keys.
- **`gen-service-accounts` Phase 4 drop** — its closed-world drop is
  instance-wide; the `replication` account is already allow-listed in
  `pkg/roles-D0YRR7WII6V1XDZR/default.php`. (Pre-existing; see the framework
  plan `2026-09-28-password-team-and-cert-service-accounts.md`.)
